How Flask, Jinja2 & PostHog Work Together

A reference for CSI 3210 — PostHog UX Analytics Lab

1. The Two Syntaxes You See in Templates

Flask uses the Jinja2 templating engine to combine Python data with HTML. There are three notations:

{{ }} Output a value

Renders a Python variable as text inside the HTML.

<p>Welcome, {{ name }}</p>
<!-- Flask replaces {{ name }} with the actual string, e.g. "Jane Doe" -->

{% %} Execute logic

Runs control flow — loops, conditionals, template inheritance. Nothing is rendered; it just controls structure.

{% for product in products %}
  <p>{{ product.title }} — ${{ product.price }}</p>
{% endfor %}

{% if user_logged_in %}
  <p>Hello, {{ user.name }}</p>
{% endif %}

{% extends "base.html" %}   <!-- inherit the shared layout -->
{% block content %}         <!-- fill in the content slot -->
  ...
{% endblock %}

{# #} Comment

Ignored by Jinja2 — never sent to the browser.

{# This is a Jinja2 comment — it won't appear in the page source #}
Key point: Jinja2 runs on the server before the HTML is sent to the browser. By the time the page reaches the user's browser, all {{ }} and {% %} tags have already been replaced with plain HTML. The browser never sees them.

2. How a Flask Route Triggers a PostHog Event

Browser request
→
Flask route (app.py)
→
ph.capture()
→
PostHog SDK
→
HTTPS POST to us.i.posthog.com
→
PostHog dashboard

Every time a user visits a page, the matching Python function in app.py runs. Before returning the HTML, that function calls ph.capture():

# app.py — the /products route
@app.route('/products')
def products():
    uid = get_uid()                         # anonymous session ID

    ph.capture(
        distinct_id = uid,                  # WHO fired the event
        event       = 'viewed_product_list',# WHAT happened
        properties  = {                     # extra context
            'category': 'UX Books',
            'count':    3,   # hardcoded — reflects len(PRODUCTS) in app.py; would increase if more books were added
        }
    )

    return render_template('products.html', uid=uid, products=PRODUCTS)

The render_template() call is completely separate — it only builds the HTML for the browser. PostHog never touches the template; it only receives what ph.capture() sends.

3. Event Naming — How Does PostHog Know Your Names?

There is no pre-registration. PostHog learns your event names the first time it receives them.

When ph.capture(event='viewed_product_list', ...) runs for the first time, PostHog:

  1. Receives the HTTPS POST from the SDK.
  2. Stores the event string "viewed_product_list" in your project.
  3. Indexes all properties (category, count) automatically.
  4. Makes the event available immediately in Live Events, Insights, and Funnels.
You invented the names. 'viewed_product_list', 'added_to_cart', 'completed_purchase' — these are arbitrary strings defined in app.py. PostHog has no schema; it accepts any event name and any properties you send.

Naming convention used in this lab

Event names follow the snake_case verb + noun pattern — the same convention used by most analytics teams:

page_view             # generic page visit
viewed_product_list   # browsed the product catalogue
added_to_cart         # picked a book
started_checkout      # reached the checkout form
completed_purchase    # order confirmed
$identify             # PostHog reserved event — links UUID to a real person
Reserved names: PostHog reserves events that start with $ (e.g. $identify, $pageview, $set). These trigger special behavior inside PostHog — do not use $ prefixes for your own events.

4. How $identify Links a UUID to a Real Person

Before checkout, every event is tied to an anonymous UUID like a3f9c2d1-.... At checkout, the user submits their name and email. The app then fires a special event:

ph.capture(
    distinct_id = uid,          # same UUID used all session
    event       = '$identify',  # PostHog reserved — triggers identity merge
    properties  = {
        '$set': {               # $set writes values to the Person profile
            'name':   'Jane Doe',
            'email':  'jdoe@oakland.edu',
            'course': 'CSI3210',
        }
    }
)

PostHog merges the UUID session with the named person profile. All events fired before the identification — page_view, added_to_cart, etc. — are retroactively attributed to that person in the People dashboard.

5. Properties — What Gets Indexed

Every key you include in properties={} becomes a filterable field in PostHog:

ph.capture(
    distinct_id = uid,
    event       = 'added_to_cart',
    properties  = {
        'product_id':   'p2',
        'product_name': 'The Design of Everyday Things',
        'price':        24.99,
    }
)

In PostHog you can then:

  • Filter funnels by price > 30
  • Group insights by product_name
  • Build cohorts of users who added a specific product_id
No schema required. PostHog discovers new property keys automatically on first receipt. The only cost of sending many properties is storage — keep them meaningful.

6. sync_mode=True — Why It Matters in a Lab

In production, the PostHog SDK batches events and sends them in the background to avoid slowing down your app. In this lab we set:

ph = Posthog(project_api_key=POSTHOG_API_KEY, host=POSTHOG_HOST, sync_mode=True)

sync_mode=True forces every ph.capture() call to send immediately and wait for the response before continuing. This means events appear in Live Events the moment you visit a page — essential for the lab so users can watch events stream in real time.

7. First Event — Route & Template Side by Side

The first ph.capture() fires the moment a user opens http://127.0.0.1:5000/. Here is what runs on the server (app.py) and what the user sees in the browser (home.html):

app.py — Flask route 

@app.route('/')
def home():
    uid = get_uid()
    # ← first capture of the session
    ph.capture(
        distinct_id = uid,
        event       = 'page_view',
        properties  = {
            'page':  'home',
            'title': 'ShopUX — UX Design Books',
        }
    )
    return render_template(
        'home.html',
        uid=uid      # passed to template
    )

home.html — Jinja2 template 

{% extends "base.html" %}
{% block title %}Home{% endblock %}
{% block content %}

<h1>Welcome to ShopUX</h1>

<div class="card">
  <p>PostHog event fired:
    <span class="badge">
      page_view {page: 'home'}
    </span>
  </p>
  <a href="/products"
     class="btn btn-primary">
    Browse Books →
  </a>
</div>

{% endblock %}
What to notice: ph.capture() runs before render_template(). The event reaches PostHog while Flask is still assembling the HTML — the browser and PostHog receive their responses independently. The template has no knowledge of PostHog; it only displays a badge to inform the user which event was fired.
